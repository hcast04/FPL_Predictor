## The weekly output

The patched notebook ends Section 12 with a single **execution card**: chip,
transfers, starting XI, ordered bench, captain and vice in one block, with the
deadline, the projected score and any warnings. Run the notebook, read the last
cell, execute it. Nothing else needs assembling by hand.

It fails loudly: if a variable is missing it names it rather than printing a
partial team.

## Quickstart

```bash
./run.sh
```

Creates a virtualenv if needed, downloads ~20 MB of archived gameweek data from
`vaastav/Fantasy-Premier-League`, then prints the evidence, the unit tests, the
out-of-sample validation on two held-out seasons, and a noise-context table.

```bash
./run.sh --quick     # skip the model fits
./run.sh patch       # regenerate FPL_Predictor_v2.6.ipynb from the original
./run.sh notebook    # open the patched notebook in Jupyter
```

Everything is reproducible from the original notebook: `./run.sh patch` applies
ten anchored edits and aborts without writing if any anchor is missing or
ambiguous, so the diff can be audited rather than trusted.

## Pushing — this repo is `hcast04`, not the work account

`gh` on this machine is logged in to two GitHub accounts, and its credential
helper hands git whichever one is **active**. So a push from here can be
rejected with

    remote: Permission to hcast04/FPL_Predictor.git denied to hcastanos-mdmsystems

even though the commit author is correct -- the author and the authenticated
pusher are different things, and only the first is set by `user.email`.

Bind the repo to the right account once, after cloning:

```bash
U=hcast04
git config --local --add credential.https://github.com.helper ""
git config --local --add credential.https://github.com.helper "!f() { test \"\$1\" = get && printf 'username=$U\\npassword=%s\\n' \"\$(/usr/bin/gh auth token --user $U)\"; }; f"
```

The first `--add` resets the inherited global helper chain for github.com; the
second asks `gh` for that **named** account's token rather than the active one.
Nothing global changes, no other repo is affected, and no token is written to
disk -- it is read from the `gh` keyring at push time.

Keep the helper on one line. A shell line-continuation inside the quoted value
does work, but only because `sh` re-parses the stored string, which is not
worth relying on.

Verify without pushing anything:

```bash
printf 'protocol=https\nhost=github.com\n\n' | git credential fill  # -> username=hcast04
git push --dry-run origin HEAD:refs/heads/_cred_check                # write auth, creates nothing
```

This lives in `.git/config`, which is not tracked, so a fresh clone needs it
again. If the token is ever revoked the helper returns an empty password and
the push fails with a plain 403, rather than silently falling back to the
other account.

## The headline finding

FPL's `expected_assists` is not on the same scale as a realised assist, and the
notebook used it as one:

```python
result["xp_assists"] = 3.0 * (predicted_xa_per90 * minute_fraction)
```

Pooled 2023-26, players with minutes > 0:

| Position | Assist pts awarded | 3 × xA (what the model used) | Ratio |
|---|---:|---:|---:|
| DEF | 2,016 | 1,619.6 | 1.24 |
| MID | 5,733 | 4,254.8 | 1.35 |
| FWD | 1,170 | 555.5 | 2.11 |

**844 assist points per season** were structurally invisible. The gap scales
with both xA and minutes, which reproduces the "high-minutes, high-points
players carry the worst error" pattern recorded in the project audit log.

`expected_goals` needs no such correction — league-wide goals/xG is 0.94–1.00.

## v2.6.1 changes after audit

- **F4 (goalkeeper goal = 6) withdrawn — it was wrong.** Current FPL pays 10
  for a goalkeeper goal; the notebook's original value was correct.
- **F2 mask moved** before `add_historical_player_features()`, so the rolling
  and career xG/xA features are built from clean data too, not just the targets.
- **Goal conversion OFF by default** (goals/xG is already ~1.0).
- **Two state bugs fixed**: the fold builder returns early on a cache hit, so
  conversion factors could leak across seasons; and the premium-attacker layer
  rebuilt attacking xP without the conversion, silently reverting F1.
- **F3 validated separately** — correct, but decision impact is negligible.
- **Captain conclusion withdrawn** — the old script tested the wrong rule.

See `fixes/AUDIT_RESPONSE.md`.

## What this is actually worth, in season points

Per-gameweek metrics are hard to read. Translated into season-end points by
picking the best legal XI each week (unconstrained — no budget or transfers,
so only the deltas mean anything):

| Fold | v2.6 vs v2.5 | 95% CI over 38 GW |
|---|---:|---|
| 2024-25 | **+17.3** | [−49, +84] |
| 2025-26 | **+3.5** | [−43, +50] |

Positive in both folds, neither significant. **Merge it for correctness, not
for expected points** — the "+2.2 top-10 points per gameweek" headline
overstated the real benefit roughly five-fold.

A direct gradient-boosted model and a component/GBM blend were both tested and
**rejected** by predeclared gates. See `fixes/ML_AND_SEASON_POINTS.md` — it
also explains why top-10 and NDCG disagree with legal-XI selection, which
matters for how this project validates anything.

## Where the points actually are

Chip timing had never been validated. It is worth far more than the forecast layer:

| Lever | Points per season |
|---|---:|
| **Chips** (TC + BB + FH, current rule vs never playing them) | **~92** |
| **Wildcard** (threshold rule vs never playing it) | **~99** |
| Forecast layer (v2.6 vs v2.5) | ~3–17 |

The notebook's chip rule beats random timing by +37/season on average, and
captures 76% of the hindsight maximum **in the second half**. Before GW19 it
adds nothing — every double and blank gameweek in both test seasons falls in the
second half, so its structural trigger cannot fire. That first-half gap is
mostly *not* recoverable: predicted chip value scores below random there.

**CORRECTION:** the wildcard result above was measured on forecasts carrying
the v2.6 assist conversion, which later failed its gate on the real pipeline.
Re-run with it off, the notebook's existing rule (74.0) **beats** threshold-only
(70.5). Patch P14 is withdrawn — set `V26_WILDCARD_THRESHOLD_ONLY = False`.
See `fixes/CHIP_TIMING.md`. Its +10
uplift bar is reachable — that is 1.84 points/gameweek over a 6-week discounted
horizon.

Solver quality is itself a lever: replacing a greedy squad rebuild with the
exact MILP in `fixes/squad_optimizer.py` raised the wildcard oracle by 45% and
turned several apparently value-destroying policies positive.

The failure mode that costs real points is not bad timing (±5 vs random) but
never playing the chips at all (−92). See `fixes/CHIP_TIMING.md`.

## Caveats worth reading before relying on this

- The validation harness is an independent re-implementation, not the real
  notebook. Re-check the §7.5 bias table on the actual pipeline before
  promoting the fix to production.
- The fix improves squad and transfer ranking. It does **not** improve
  captaincy (measured: −0.08 pts/GW, inside noise).
- Chip timing thresholds in the notebook are hand-chosen and have never been
  validated against any alternative.
- The transfer-policy scorecard that selected `greedy_1gw_no_hits` was run with
  chips disabled, and v2.6 changes the forecast it depends on.
